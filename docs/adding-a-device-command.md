# Adding a Device Command

How to add a new device-management command so the device agent can execute it,
the AI can propose it, and the technician can compose it manually — without the
four lists drifting apart.

## The rule

A command type is declared in **one place** — `ai/actions.py` `ACTION_REGISTRY` —
and the AI-facing reference and tool docstring are generated from it. The device
agent and the frontend template are the two remaining hand-maintained spots,
guarded by tests.

## Files to touch

### 1. Device agent (execution)

`backend/src/homepot/agent/utils/command_poller.py`:

- Add the name to `COMMAND_TYPES`.
- Add the permission to `REQUIRED_PERMISSION`.
- Add a handler function and a dispatch branch in `_process_command_impl`
  (mirror an existing sibling, e.g. `_restart_service`).
- Optionally add a branch in `_describe_executed_command` so the executed OS
  command is shown verbatim in push history.

### 2. AI registry (single source of truth)

`ai/actions.py` `ACTION_REGISTRY`:

- Add an `ActionSpec` with `name`, `command_type`, `risk_tier`, `reversible`,
  `required_permission`, `min_role`, `description`, and `required_params`.

That one entry automatically updates:

- the `propose_device_action` tool docstring (generated by
  `allowed_actions_summary`), and
- the `[COMMAND PAYLOAD REFERENCE]` system-prompt block (generated by
  `_build_command_payload_reference`).

### 3. Executor title (optional)

`backend/src/homepot/app/ai_ops/executor.py` `_AI_COMMAND_TITLES`:

- Add a friendly title. If omitted, the fallback
  `action.replace("_", " ").title()` is used, which is usually correct.

### 4. Frontend compose-command template

`frontend/src/pages/Device/PushReview.jsx` `COMMAND_TEMPLATES`:

- Add a template entry (`label`, `action`, `permission`, `defaultData`,
  `description`) so technicians can compose it from the dashboard.

## Special cases

- `rollback_config` reuses `update_config`'s `command_type`. The registry
  generator skips any action whose `name != command_type`, so it is not emitted
  as a distinct command type.
- `ping`, `request_permission`, and `status_request` are internal command types
  that the AI never proposes; they are listed statically in the reference and do
  not need an `ACTION_REGISTRY` entry.

## Tests that keep the lists aligned

- `backend/tests/test_ai_delegation_phase1.py` — asserts the registry's exact
  action set and tiering, and that the proposal tool docstring lists every
  registered action.
- `backend/tests/test_ai_enriched_context.py` — asserts the command payload
  reference covers every `COMMAND_TYPES` entry.
- `backend/tests/test_agent_command_polling.py` — asserts the agent handler
  returns the expected result shape.

Run the backend suite and `mkdocs build --strict` before opening a PR.
