## What is UQ and why does it matter here?

### What is Uncertainty Quantification?

When a software system takes inputs and produces outputs, its behaviour is usually
tested at a small number of fixed, hand-picked input values. That is fine for checking
that specific cases work correctly, but it tells you nothing about how the system
**behaves across the full range of inputs it will realistically encounter in
production**.

**Uncertainty Quantification (UQ)** is the discipline of systematically exploring how
variability (or *uncertainty*) in the inputs of a model propagates through to
variability in the outputs. The key questions UQ answers are:

- **What is the distribution of the output?**  
  If inputs are not fixed but can take a range of values, what range of outputs should
  we expect? What is the most likely output? What are the extremes?

- **Which inputs matter most?**  
  If the output varies a lot, is that because of input A, or input B, or some
  combination? This is called **sensitivity analysis**. It identifies which parameters
  are the critical ones to monitor, control, or measure more precisely.

UQ is established practice in fields such as climate modelling, aerospace engineering,
and medical simulation — wherever decisions depend on computational models and it is
important to understand those models' behaviour under the full range of plausible
conditions, not just specific test cases.

### What is EasyVVUQ?

[EasyVVUQ](https://github.com/UCL-CCS/EasyVVUQ) is a Python library that provides a
simple, structured way to run UQ campaigns on any existing code. It was designed
specifically for cases where you have an existing model (a simulation, a scoring
function, an AI component) and want to understand its behaviour without rewriting it.

EasyVVUQ works by:
1. Generating many carefully-chosen input combinations (a **sample set**).
2. Running your model once for each combination.
3. Collecting all the outputs and performing statistical analysis.

### Why is UQ relevant to HOMEPOT?

HOMEPOT-Client includes an AI layer (`ai/`) that makes automated decisions about
device health and failure risk. Those decisions depend on scoring functions with
**manually chosen weights and thresholds**. Nobody has previously checked:

- Whether the chosen weights actually reflect the intended priorities.
- Whether some metrics are redundant (changing them makes no difference to the score).
- Whether the thresholds in `ai/config.yaml` are where the code actually reads them from.
- Whether realistic production device states (not just the specific test cases)
  produce sensible scores.

UQ provides a principled, quantitative way to answer all of these questions.

## Setup

### 1. Clone EasyVVUQ (if you don't already have it)

```bash
git clone https://github.com/UCL-CCS/EasyVVUQ.git /path/to/EasyVVUQ
```

### 2. Install EasyVVUQ in editable mode into the homepot venv

From the `homepot-client` root:

```bash
.venv/bin/pip install -e /path/to/EasyVVUQ
```

This follows the
[official install instructions](https://github.com/UCL-CCS/EasyVVUQ#installation)
and pulls in all required dependencies (chaospy, dill, SQLAlchemy, etc.) into the
existing homepot venv. No separate venv is needed.

> **Why editable (`-e`)?**  Changes to the EasyVVUQ source are immediately reflected
> without reinstalling — useful when developing or patching the library.

### 2b. Install the remaining UQ dependencies

EasyVVUQ does not pull in every package the studies need. Install the rest from the
UQ requirements file:

```bash
.venv/bin/pip install -r uq/requirements.txt
```

### 3. Run a study

Each study is self-contained. From the `homepot-client` root:

```bash
# Study 1
HOMEPOT_PATH=$(pwd) .venv/bin/python uq/study1_anomaly/run_anomaly_uq.py

# Study 2
HOMEPOT_PATH=$(pwd) .venv/bin/python uq/study2_simulator/run_simulator_uq.py

# Study 3
HOMEPOT_PATH=$(pwd) .venv/bin/python uq/study3_push/run_push_uq.py
```

Results are printed to stdout. Plots are saved to the `figs/` subdirectory of each
study (gitignored, created at runtime).

## Where does UQ get its data?

**UQ studies do not read from the database or from live device telemetry.** They use
**synthetically sampled inputs** generated by EasyVVUQ's samplers (PCE, Saltelli/
MCSampler). Each sample is a specific combination of metric values; the model
under analysis (`AnomalyDetector.check_anomaly()` or the push delivery model) is
run once per sample, and the outputs are collected and analysed statistically.

In other words, UQ explores how the **model behaves across the full range of
plausible inputs** — it does not analyse real device data. This is deliberate:
the goal is to understand the model's sensitivity and robustness, not to audit a
specific device's history.

For contrast, the *production* anomaly path (not UQ) does use real data:

- `anomaly_scan.py` (background, scheduled) reads the latest `DeviceMetrics` row
  from the database for each active device and runs the detector on it.
- The `/api/ai/analyze` endpoint accepts a caller-supplied metrics dict (often
  from a live device or the simulator).
- The Dashboard displays real metrics and anomaly scores from the database.

UQ and production detection share the same model (`AnomalyDetector.check_anomaly`),
but UQ feeds it synthetic samples while production feeds it real telemetry. This
separation means UQ can stress-test the detector against edge cases that may
never have appeared in production data yet.

## What each study does

Each study answers a different question about a different model. They are kept
separate (rather than combined into one analysis) because they use different
sampling strategies, different input sets, and different quantities of interest.

### Study 1 — Anomaly Detector Sensitivity (`study1_anomaly/`)

- **Model under analysis:** `ai/anomaly_detection.py` — `AnomalyDetector.check_anomaly()`,
  the rule-based scorer that turns device metrics into an anomaly score (0.0-1.0).
- **Question:** Do the hand-tuned weights and thresholds reflect the intended
  relative importance of the metrics? Which metrics actually drive the score
  across the realistic range of device states?
- **Inputs (7):** `cpu_percent`, `memory_percent`, `disk_percent`, `error_rate`,
  `network_latency_ms`, `flapping_count`, `consecutive_failures`.
- **Method:** Polynomial Chaos Expansion (order 2) + Sobol indices, 2 187 samples.
- **Outputs:** statistical summary (mean, std, percentiles) and first-order Sobol
  indices for `anomaly_score`.
- **When to use:** Engineering tuning — checking that the weights/thresholds in
  `ai/config.yaml` are sensible and that no metric is redundant.

### Study 2 — Simulator Scenario Boundary Validation (`study2_simulator/`)

- **Model under analysis:** the same `AnomalyDetector.check_anomaly()`, but fed
  by `DeviceSimulatorEndpoint._generate_metrics_for_scenario()` so each scenario
  (healthy, high_cpu, low_memory, high_errors, degraded, offline) gets its own
  input distribution.
- **Question:** Does the detector behave correctly in each operational regime?
  (e.g. a healthy device should score ~0; a degraded device should score high;
  CPU spikes alone should not trigger an alert.)
- **Inputs (7):** same as Study 1, but sampled per-scenario with scenario-
  appropriate ranges (some params pinned near zero for "always-off" scenarios).
- **Method:** MCSampler (Saltelli plan) + QMCAnalysis (Sobol with bootstrap CIs),
  ~16 200 samples total across six scenarios.
- **Outputs:** score distributions, Sobol indices per scenario, misclassification
  rates (false positives on healthy, false negatives on degraded/offline).
- **When to use:** Validation — confirming the detector's behaviour across
  realistic device states, not just specific test cases.

### Study 3 — Push Notification Delivery Reliability (`study3_push/`)

- **Model under analysis:** a deterministic expected-value model of push
  notification delivery (success rate × fleet size).
- **Question:** How reliable are push notifications under uncertainty in the
  per-device success rate and fleet size? Which input drives delivery variance?
- **Inputs (2):** `success_rate` (Beta prior), `num_devices` (DiscreteUniform).
- **Method:** MCSampler (Saltelli) + QMCAnalysis (Sobol), 20 000 + 12 000 samples.
- **Outputs:** expected failures, failure rate, campaign time, Sobol indices,
  P(at least k of N succeed), sensitivity to the success-rate prior.
- **When to use:** Operations — sizing push campaigns and understanding
  delivery risk under uncertain per-device success rates.

### Study 4 — Extended Anomaly Detector Sensitivity (`study4_extended/`)

- **Model under analysis:** `AnomalyDetector.check_anomaly()` (extended), now
  scoring the device-health signals added in PR #1099 (battery, temperature,
  CPU speed, Wi-Fi signal) in addition to the original seven.
- **Question:** How do the new device-health parameters affect the anomaly score?
  Which of them drive variance in each scenario?
- **Inputs (11):** the original 7 plus `battery_percent`, `cpu_temp_c`,
  `cpu_speed_mhz` (with `cpu_speed_max_mhz` as a fixed reference),
  and `wifi_signal_dbm`.
- **Method:** MCSampler (Saltelli) + QMCAnalysis (Sobol with bootstrap CIs),
  ~19 800 samples across six scenarios.
- **Outputs:** score distributions and Sobol indices per scenario.
- **When to use:** Sensitivity analysis of the extended detector; complements
  Study 2 (which stays on the original 7 params as a PCE baseline in Study 1).

### Consolidated view

Studies 1 and 2 together answer "which inputs matter most" (globally via PCE,
per-scenario via Saltelli). Study 4 extends Study 2 to the full 11-input space.
Study 3 is independent (different model, different question).

The runner logic is shared (`uq/common/runner.py`) so that adding or changing a
parameter only requires editing the study's shim (its `FLOAT_KEYS`/`INT_KEYS`
list) and its scenario distributions — not the casting or output-writing code.
